# S2 六维权重调整与全车评分重算

> 更新：评分治理已支持因子条件说明、权重设计草稿、迁移影响、两版本对比及历史归档恢复为新版本；详见README_EVALUATION_GOVERNANCE.md。

入口：系统管理 → 规则与运营配置 → 评分规则。“规则草案”入口也进入同一权重页，避免两套生效路径。

## 操作

1. 拖动六个维度条形滑块，或输入百分比。调整一项时，其余项按比例分配剩余权重，合计保持 100%。允许某维度设为 0。
2. 点击“预览分数变化”，查看全部 500 辆车的平均分变化、受影响车辆数、等级变化数，以及分数变化最大的 12 辆车。
3. 点击“提交并重算全部 500 辆车”，才会保存并切换到新评分版本。
4. 在“历史评分版本”查看原始及各次提交的评分。点击“恢复原始权重”后再预览、提交，可以生成恢复原始算法权重的新版本，旧版本仍保留。

本轮开发没有替用户选择新的正式权重；测试提交只发生在数据库副本。实际库初始展示原始权重。

## 计算口径

沿用原提交的六维证据、暴露量、先验收缩及参考分布；每个维度的新增扣分系数固定，由原始维度贡献除以原始权重取得。

`新安全分 = 100 − Σ（新维度权重 × 对应的新增扣分系数）`

安全分取 0–100 并按正式 CSV 保留 6 位小数。计算始终从不可变原始基线出发，不对上一次结果重复乘权重，因此多次修改及恢复不会累积误差。

可信度由轨迹/IMU 覆盖、有效采样和暴露量等证据计算，不随主观权重改变。IMU 缺失的不确定性预留随其权重同步调整。40 天风险概率由独立预测模型提供，本次不重训预测模型。

等级仍使用原来的排名比例：A/B/C/D 为 20%/40%/30%/10%。所以 500 辆车的各等级数量保持 100/200/150/50，但具体属于哪个等级的车辆会随安全分与排名变化。

## 提交后的联动

同一 SQLite 事务中更新：500 条当前评分、4,000 条同口径历史趋势、6,267 条扣分台账、500 条复核队列和六维规则。排名、等级、主要扣分原因、七天分差、建议与复核优先级同步更新；保留数据观察窗为 14 天。

旧的所有评分结果保存在 `scoring_version_rows`，版本与权重、操作者、时间、变化摘要保存在 `scoring_versions`。这些归档不会被当前版本覆盖。原始 CSV、只读历史索引、风险预测以及已有培训和沟通记录不因重算被修改。

管理员提交后当前页面立即更新；其他页面、司机端刷新、重新聚焦或约 15 秒内检测版本切换并重新读取数据，同时清除旧评分上下文的 AI 会话缓存。

## 一致性与权限

- 只有拥有全部车队权限的安全管理员可修改影响全车队的权重；司机和受限账号不能提交。
- 后端验证六维字段、数值范围、权重和、预览凭据及基线版本；不会仅靠前端检查。
- 重复请求幂等；别人已更新配置时旧预览被拒绝，要求重新加载后预览。
- 中途数据库失败整批回滚，不会出现部分车辆新分、部分车辆旧分。
- 旧“草案生效但不重算”接口、本地评分表的旁路导入不再用于改变这组评分结果。
- 已建立评分版本后，原建库脚本拒绝覆盖重建。更新数据源需另建独立评分基线，不能覆盖既有版本库。

本功能已接入当前本地完整数据模式（`npm run start:local`）。云端纯 PostgREST 部署如没有对应事务重算服务，会明确提示服务未配置，不能仅上传前端就认为已支持重算。
